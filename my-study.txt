社会保険料
会社員（役員を含む）が加入する国の社会保障制度である「健康保険」「介護保険（40歳以上65歳未満の場合）」「厚生年金保険」「雇用保険」「労災保険」の5つの保険にかかる保険料の総称
「健康保険料」「介護保険料」「厚生年金保険料」をまとめて（狭義の）社会保険料と呼び、「雇用保険料」と「労災保険料」をまとめて労働保険料
労災保険料以外は労使折半

厚生年金→18.3%
健康保険→協会けんぽor組合健保

健康保険・介護保険・厚生年金保険の3つ
（2026年4月からは「子ども・子育て支援金」が導入された）
40歳以上65歳未満の従業員は介護保険料が発生する

厚生年金：入社～70歳の誕生日前日
健康保険：入社～75歳の誕生日前日
介護保険：40歳の誕生日の前日が属する月～65歳の誕生日の前日が属する月の前月

資格喪失は「退職日の翌日」
月中の退職（月末以外）: 喪失日が当月になるため、前月分までの保険料が発生
月末の退職: 喪失日が翌月1日になるため、当月分（退職月）までの保険料が発生
社会保険料は「資格取得月～資格喪失日の前月」まで、月単位で発生

保険料の算定基準は報酬月額（目安）によって算出された標準報酬月額
報酬月額（目安）：基本給のほか、約淑手当、通勤手当、残業手当などを含んだ1か月の総支給額
基本賃金・諸手当（固定）・諸手当（変動）・賞与（年4回以上）・現物支給・継続的な手当
通勤手当は所得税非課税だが、報酬に含まれる
お祝い金や見舞金のような臨時のもの、年3回以下の回数で支給される賞与（ボーナス）は標準報酬月額の算定基礎には含まれない
毎年7月1日現在の全ての被保険者。
■以下の該当者は対象外
・6月1日以降に被保険者資格を取得した人
・7月に随時改定（月額変更届を提出）が行われる人
・8月または9月に随時改定が行われる予定の人（申出が必要）

随時改定（昇給・降給で2等級以上差）
固定的賃金の変動
残業手当などの非固定的賃金は対象外
固定的賃金の変動があった月以後継続した3ヶ月間（すべて17日以上）に支払われた報酬の平均額（報酬月額。残業代などの非固定的賃金も含む）から算出した標準報酬月額が、従前の標準報酬月額と比較して2等級以上の差が生じたこと。

賞与：年3回以下→「賞与支払届」
年4回以上→「賞与に係る報酬」となる。前年7月～当年6月の合計を12で割り、月々の報酬に加える→[端数処理]
年4回以上の賞与支給が就業規則や賃金規程で正式に規定されていない、異なる性質の場合にはその限りではない

月額変更届（随時改定）：報酬に変動が生じた月から3カ月間の平均報酬が、従来の標準報酬月額から2等級以上変動した場合に、4カ月目から新しい標準報酬月額が適用される

標準報酬月額：等級に分かれている
協会けんぽ→50段階
厚生年金→32段階
定時決定→4，5，6月の平均額→[端数処理]
原則として報酬の支払基礎日数（給与計算の対象となった日数）が17日以上ある月のみ
支払基礎日数の数え方は、月給制（暦日数）か日給・時給制（出勤日数）か、また欠勤控除の有無によって異なる

短時間就労者（パートタイマーなど）
1週間の所定労働時間および1ヶ月の所定労働日数が、通常の労働者の4分の3以上である被保険者
1か月でも17日以上の月がある	17日以上の月の報酬平均額をもとに決定
15日以上17日未満の月がある	15日以上17日未満の月の報酬平均額をもとに決定
3ヶ月とも15日未満	以前決定した標準報酬月額を継続

短時間労働者
週の所定労働時間が20時間以上
雇用期間が継続して2ヶ月を超えて見込まれる
賃金の月額が88,000円以上→[法律を確認]
学生ではない
特定適用事業所（※）または国・地方公共団体に勤務している （※特定適用事業所：厚生年金保険の被保険者数が常時51人以上の事業所。
1か月でも11日以上の月がある	11日以上の月の報酬平均額をもとに決定
3ヶ月とも11日未満	以前決定した標準報酬月額を継続

招待リンク先は必要です。今 Functions はこのURLを作っています。

const inviteLink = `${frontendUrl}/invitation?token=${encodeURIComponent(rawToken)}`;
なので Angular 側にこのルートが必要です。

{ path: 'invitation', component: InvitationAcceptCmp }
この画面でやることは：

URLの token を読む
token を Functions に渡す
Functions 側で tokenHash を照合
期限切れ・使用済みを確認
未ログインならサインアップ/ログインへ誘導
承認後に affiliations/{uid}_{eid} を作る
invitation を accepted に更新
つまり、次に作るべきは 送信ボタンから sendInvitationMail を呼ぶ処理、その次に /invitation?token=... の受け入れ画面と承認Functions です。


その方針、かなり現実的で安全寄りです。  
**招待メールの宛先アドレスを本人確認用に使い、その後のログイン用アカウントは別メールでもOK** という設計ですね。

流れはこう整理できます。

```text
1. 会社が従業員の連絡先メールに招待を送る
2. 従業員が招待リンクを開く
3. 画面で「招待を受け取ったメールアドレス」を入力
4. token + 入力メールアドレスを照合
5. 一致したら招待確認画面へ
6. アカウント作成 or 既存アカウントでログイン
7. ログイン後に招待を承認
8. affiliations/{uid}_{eid} を作成
```

この場合、Firestore の invitation はこう持つのがよいです。

```ts
{
  contactEmail: "employee@example.com", // 招待メールを送った宛先
  inviteeName: "山田 太郎",
  tokenHash,
  status: "sent",
  role: "member",
  establishmentId,
  establishmentName,
  invitedBy,
  invitedByEmail,
  expiresAt,
  createdAt,
  sentAt
}
```

`checkInvitationToken` は token だけでは詳細を出しすぎず、まずメール入力を促す程度でOKです。

```ts
checkInvitationToken({ token })
```

返す情報：

```ts
{
  valid: true,
  requiresContactEmail: true
}
```

次に、入力されたメールで確認します。

```ts
verifyInvitationContactEmail({ token, contactEmail })
```

やること：

```text
1. tokenHash で invitation 検索
2. status が sent/pending か確認
3. expiresAt 確認
4. contactEmail と invitation.contactEmail を比較
5. 一致したら invitation概要を返す
```

返す情報：

```ts
{
  verified: true,
  inviteeName,
  contactEmail,
  establishmentName,
  role
}
```

その後、ユーザーに選ばせます。

```text
この招待は 山田 太郎 さん宛です。
株式会社〇〇 に参加します。

[アカウント作成]
[ログイン]
```

最後にログイン済み状態で：

```ts
acceptInvitation({ token, contactEmail })
```

ここでも必ず再チェックします。

```text
1. auth.uid 必須
2. tokenHash 検索
3. contactEmail 一致確認
4. status / expiresAt 確認
5. affiliations/{uid}_{eid} 作成
6. accounts/{uid} 更新
7. invitation を accepted に更新
```

この設計の良い点は、リンクを転送された人が勝手に参加しにくいことです。  
token だけでなく「招待を受け取ったメールアドレス」も必要になるからです。

注意点は、入力メールの比較時に正規化することです。

```ts
function normalizeEmail(email: string): string {
  return email.trim().toLowerCase();
}
```

保存時も比較時も小文字化してください。

結論として、この仕様なら **ログイン用メールと招待先メールを分離しつつ、招待先メールによる本人確認もできる**のでバランスが良いです。
